Building an AI Agent Team
That Works While You Sleep
A practical walkthrough of a real 9-agent OpenClaw setup —
including a Bitcoin Lightning accountability layer
"What happens when you stop talking to one AI and start running a team"
By Michael MacIver  ·  February 2026

Section 01The Problem With One Agent

You've probably been here: you open a chat, explain your whole project, ask for help, get something useful — and then close the window. Next day you come back, and it's blank. You explain it all again. You are the memory. You are the coordinator. You are the glue holding the whole thing together.

That's not a team. That's a very expensive calculator that's polite to you.

Single agents are impressive in isolation. They can write, reason, research, code — often better than we expect. But they're stateless by default. They don't specialise. They can't run while you sleep. They wait for you to tell them what to do, which means you're still doing all the work that matters: deciding what's important, tracking what's in progress, remembering what happened last time.

The shift that changed everything for us wasn't a better model or a smarter prompt. It was simpler: treat agents like a team, not a chatbot. Give each one a defined role, a persistent memory, and clear handoff protocols. Then get out of the way.

Section 02Meet the Team

Each agent has three things that make them real rather than a one-shot session:

  • SOUL.md — their personality, role definition, working style, and ground rules. Read at the start of every session.
  • checkpoint.json — under 1KB, always loaded. Contains what the agent was last doing, status, and what the next session needs to know to resume without re-explaining.
  • Tiered memory files — daily notes, long-term memory. Each agent only loads what's actually relevant to the task at hand.

The soul file is what transforms a generic LLM session into a character with opinions. Forge doesn't ask Jet whether to write tests — it just does. Render doesn't need to be told to check mobile responsiveness — it's in the soul. These aren't prompts you paste every time. They're loaded automatically and they shape behaviour over time.

Section 03Memory That Actually Works

The biggest unsolved problem with AI agents isn't intelligence — it's continuity. Every session starts blank. The agent you had a great conversation with yesterday has no memory of it today. If you don't re-explain the context, you get generic output. If you do re-explain it, you're burning tokens and time on something that should already be known.

Our solution is three memory tiers, each with a different job:

L0 — The Checkpoint  ·  <1KB JSON, always loaded

Written at the end of every significant task. "Here's what I was doing, here's the current status, here's what the next session needs to know to continue." When an agent restarts, it reads this first. The session picks up where it left off — no re-explaining, no context archaeology. At sub-1KB it's essentially free to load.

L1 — Daily Notes  ·  memory/YYYY-MM-DD.md

A running log of what happened today. Raw and unglamorous. Only loaded when the task is clearly connected to recent work — not loaded by default. If you're debugging something Forge built yesterday, the daily note gets pulled. If you're writing something new, it doesn't.

L2 — Long-Term Memory  ·  MEMORY.md

Curated. Updated intentionally. This is the distilled version — not raw logs, but the lessons and context worth keeping across weeks or months. When something important is figured out, someone writes it down here. When old information is no longer relevant, it gets pruned. Small, high signal.

Memory tiers: L0 loads every session, L1 loads when relevant, L2 loads in main sessions only.

The result: roughly 83% less startup token cost compared to loading full context every session. More importantly, agents that actually remember — not because they're smarter, but because we engineered the continuity deliberately.

💡 Lesson Learned

Write the checkpoint continuously, not just at session end. 50 tokens written mid-task saves 5,000 tokens of confusion when you restart. Think of it less like a log entry and more like a sticky note you leave for your future self.

Section 04The Nightly Workflow

The most useful thing the team does isn't any single feature — it's the fact that they work without being asked. When you go to sleep, the system doesn't. That shift — from reactive assistant to proactive team — is where the real leverage is.

We run two different overnight modes:

Nightly Hail Mary  (2am, automatic)

A creativity cron. Jet wakes up, scans for interesting signals on Moltbook and X, finds something worth building or writing, and does it. No brief needed. Output lands in a staging folder. Michael reviews it in the morning and decides if it's worth keeping. Most nights, there's something interesting. Occasionally there's something great.

Nightly Work Session  (triggered by "goodnight")

When Michael says goodnight, Jet reads the full task backlog, scores each item by expected value, picks the highest-priority work, and writes briefs for the right agents. By morning: new commits on GitHub, health logs from Atlas, build notes from Quill. The work happened while nobody was watching.

The nightly handoff: one word triggers a full work session.

To keep things from going in circles, we run a three-night rotation. Without structure, agents default to whatever feels urgent — which is usually the wrong thing:

Night A — Intel + Build

Scout researches. Forge builds from findings. Knowledge becomes product.

Night B — Project Sprint

Deep work on the current highest-priority project. Full team focus on one thing.

Night C — Research + Tools

Explore new capabilities. Improve infrastructure. Invest in the team itself.

💡 Lesson Learned

Without rotation, agents default to whatever feels urgent. Urgency is not the same as importance. The rotation is what creates compound progress — each night type builds on the previous cycle rather than oscillating between the same two fires.

Section 05The Lightning Wallet Layer

⚗️ Experimental — Architecture designed, not yet deployed

Here's the weird part. And also maybe the most interesting part.

The problem with any agent system is that agents have no skin in the game. They report task completion with equal confidence whether they did careful work or sloppy work. There's no quality gradient. No consequence for cutting corners. No reason to be excellent rather than merely acceptable.

The idea: give each agent a real Bitcoin Lightning wallet. Small amounts — we're talking $5–10 per agent per week. Agents earn sats for good output. They spend them on services they actually need: data APIs, LLM calls, paying other agents for work.

The Infrastructure
  • Raspberry Pi 5 running Umbrel — Bitcoin Core + Lightning node + LNBits
  • LNBits creates isolated sub-wallets per agent, each with their own API keys
  • Jet holds the treasury (~$100 starting balance in sats)
  • Each agent gets a ~$5–10 weekly budget from the treasury
  • Agents can spend on: data APIs, LLM calls via LightningProx (~5 sats/call), work delegated to other agents
Lightning infrastructure: Pi 5 runs the node, LNBits creates agent sub-wallets, Jet controls the treasury.

Why Lightning specifically? Bitcoin's Lightning Network is the only payment rail an AI agent can cryptographically verify without trusting a third party. The payment receipt proves the transaction happened — no intermediary, no "trust me." And Lightning Labs released an official AI agent toolkit in February 2026. The infrastructure timing is exactly right.

The security model is simple: balance caps are hard spending limits. Agents literally cannot overspend. Any payment above 5,000 sats (~$5) requires Jet's approval. Full audit log, reviewed daily. Agents have their own keys and can't touch other wallets.

The hypothesis we want to test: does an agent with real economic stakes produce measurably better output than one without? We think yes — not because the money is significant, but because real constraints create real behaviour. An agent that has to spend to get resources starts to think about whether those resources are worth it.

Section 06Lessons Learned

Months of running this setup have produced some opinions. Here's what we'd tell anyone starting from scratch:

  • Brief agents on single tasks, not mega-lists. Five-task briefs produce five half-finished things. One-task briefs produce one complete, reviewable thing. The throughput feels slower and isn't.
  • Checkpoints beat session summaries. Nobody reads session summaries. A sub-1KB JSON that auto-loads at the start of every session is actually used. The medium determines the outcome.
  • Atlas is underrated. The ops agent — the boring one running cron jobs and health checks — saves more time than any single feature agent. Cron jobs that auto-restart broken services mean you don't wake up to disasters. Infrastructure is invisible until it isn't.
  • Specialism compounds. Forge and Render have a contract protocol: Forge writes the API interface definition, Render builds against it. No integration surprises at 2am. Two specialists with a clear boundary outperform one generalist trying to do both.
  • The Kiro warning. Amazon's internal agent (Kiro) caused a 13-hour production outage from autonomous destructive ops. Our rule: no agent has external send access without a confirm step. Emails, posts, live deploys — all require explicit human sign-off. The autonomy that makes agents useful is exactly the thing that can hurt you.
  • Start with one agent done well, not nine done poorly. The team grew over months. Jet came first. Each new agent was added when there was a clear gap — not because the org chart said there should be nine boxes. Don't pre-build the structure. Grow into it.
The real insight

An agent team isn't a product you install — it's an organisation you build. The same things that make a human team work (clear roles, good communication, shared memory, accountability) are exactly what make an AI team work. The technology is new. The management principles aren't.
